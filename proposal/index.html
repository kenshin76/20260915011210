SUMMARY

핵심 요약 6가지

제안서 전문에서 판단에 직접 쓰이는 여섯 문장만 옮겼습니다. 이후 각 절에서 근거와 수치를 상세히 설명합니다.

01신규 구축을 권합니다

현재 확인된 범위와 전제에서는 신규 구축을 권합니다. 침해 흔적이 남아 있을 가능성을 배제할 수 없는 소스는 진단 비용을 들여도 「깨끗하다」를 증명할 수 없습니다. 상품 5종 규모에서는 신규 구축이 비용과 잔존 위험 양쪽에서 유리하다고 판단했습니다. §4.4

02DB 탈취만으로는 상품권 번호를 확인할 수 없게 합니다

번호를 암호화해 저장하고, 복호화는 공개 쇼핑몰과 권한이 분리된 내부 전용 기능에서 수행합니다. 비정상 복호화 요청은 주문별 일회용 권한·요청 총량 제한·이상 탐지로 차단합니다. 검수 때 실제 DB 덤프로 평문이 없음을 보여 드립니다. §7.3 ①

03공개 웹 에디터를 쓰지 않습니다

사고의 경로였던 공개 웹 에디터를 제외합니다. 팝업·공지는 허용 목록 기반 입력으로 바꾸고, 파일 업로드 경로에서는 실행 자체가 불가능하도록 서버를 구성합니다. §6.7

04운영해 본 구조를 적용합니다

2026년 7월 기준 쿠폰 발급·교환 시스템 13년 1개월(법인 설립 전 모회사·전신 조직 수행분 포함), 통합 빌링 시스템 9년의 상용 운영 실적이 있습니다. §2

0554일 안에 구축·복구 검증을 마치고 6일을 예비 기간으로 둡니다

공고 기간 60일 중 제작 44일 + 인수·배포·검수 10일이며, 나머지 6일은 PG·알림톡 심사 지연을 흡수할 예비입니다. 백업은 운영 환경과 분리해 암호화하고, 빈 환경에서 실제 복구해 확인합니다. §6.6·§9.1

06대표님 혼자서도 운영할 수 있게 인계합니다

40 MD 안에서 수행할 범위와 제약을 먼저 확정하고, 소스·서버·계정·운영 문서를 인계해 특정 업체에 종속되지 않도록 합니다. §4.3·§11.5~11.6

01

공격자의 순서로 다시 읽은 이번 사고

공고에 적어 주신 두 번의 사고를 공격자가 밟은 순서로 되짚고, 각 단계를 무엇으로 끊는지 붙였습니다. §3.3

1

관리자 화면을 찾음

관리자와 쇼핑몰이 같은 서버·같은 도메인에 있었습니다.

서버와 도메인을 분리하고 관리자는 IP 허용 목록으로 접근을 제한합니다. §7.3
2

팝업 등록의 에디터로 PHP 파일 업로드

공개 에디터의 업로드 기능이 확장자를 제대로 막지 않았습니다.

에디터를 쓰지 않습니다. 업로드는 이미지 전용이며 확장자·실제 파일 내용·용량을 모두 검사합니다. §6.7
3

업로드한 파일을 웹으로 실행 (웹쉘)

업로드 경로에서 스크립트 실행이 허용됐습니다.

업로드 파일은 웹에서 실행할 수 없는 경로에 저장하고, 파일명을 난수로 바꿔 주소를 추측할 수 없게 합니다. §7.3
4

웹쉘로 DB에 접근

DB 계정 하나로 모든 데이터에 접근할 수 있었습니다.

상품권 번호는 암호화해 저장하고, 푸는 일은 쇼핑몰 서버가 하지 않습니다. 쇼핑몰이 장악되어도 열쇠가 그곳에 없어 평문을 얻지 못합니다. §7.3 ①
5

(이전 사고) SQL 인젝션으로 데이터 조회

사용자 입력이 그대로 쿼리에 들어갔습니다.

모든 쿼리를 값과 문장을 분리하는 방식으로만 작성하고, 문자열을 이어 붙여 쿼리를 만드는 코드는 코드 자동 검사로 막습니다. §9.2

이 표의 4단계가 이번 과업의 핵심입니다

침입 가능성을 0으로 단정하지 않고, 쇼핑몰 서버나 DB가 침해되어도 저장된 번호가 한 번에 평문으로 유출되지 않게 하는 것이 목표입니다. 정상 사용자가 번호를 확인하는 경로까지 악용될 가능성은 §7.3 ①의 일회용 권한·호출 제한·이상 탐지로 낮춥니다.

코드만 새로 만드는 것으로는 충분하지 않습니다. 기존 서버는 사고 당시 상태를 보존한 스냅샷에서 읽기 전용으로 점검하고, 운영 전환은 새로 설치한 OS와 새 계정으로 구성합니다. 전환 시 SFTP/SSH·DB·PG·도메인·알림톡·암호화 키와 세션 비밀값을 교체하고, 기존 서버는 네트워크에서 격리합니다.

이 과업의 난제 3가지 §3.2

난제 01「기존 소스가 깨끗하다」는 증명할 수 없습니다

웹쉘과 백도어는 정상 파일이나 코드에 숨을 수 있어, 점검 결과도 「확인한 범위에서 발견되지 않음」으로 한정해야 합니다.

대응 — 기존 코드는 재사용하지 않고 새로 구축합니다. 기존 환경은 침해 경로와 이관 데이터의 무결성을 확인하는 범위에서 읽기 전용으로 점검합니다.

난제 02표준 산정과 확보 투입량의 차이가 큽니다

요청 범위의 표준 산정은 95~135 MD이지만, 공고 예산으로 확보되는 투입량은 40 MD입니다.

대응 — 구현 방식을 단순화하고 대체안·범위 상한을 함께 적용합니다. 화면은 서버 렌더링으로 통일하고, 카드·휴대폰·간편결제는 PG 한 곳으로 묶습니다.

난제 03설계 원칙 자체를 바꿔야 합니다

기존 사고는 알려진 취약 구성 요소를 계속 사용하고 업로드 파일의 실행을 허용한 데서 시작됐습니다.

대응 — 공개 웹 에디터를 제외하고 업로드 경로의 실행을 차단합니다. 외부 라이브러리는 이름과 버전을 문서로 남겨 취약점 공지 시 영향 여부를 바로 확인할 수 있게 합니다.

02

번호를 지키는 세 가지 구조

나머지 화면은 일반적인 쇼핑몰 구성으로 성립합니다. 이 세 가지는 공고의 사고 경험과 직접 맞물리므로 따로 적습니다. §7.3

「열쇠를 숨기는 것」이 아니라 「복호화 권한을 쇼핑몰과 분리하는 것」입니다.

먼저 짚고 갑니다

「번호를 암호화하고 열쇠를 서버 파일에 두면 안전하다」는 설명은 웹쉘에는 통하지 않습니다. 웹쉘은 쇼핑몰 프로그램과 같은 권한으로 실행되므로, 그 프로그램이 읽을 수 있는 열쇠는 웹쉘도 읽습니다. 열쇠를 숨기는 것만으로는 실제로 겪으신 사고를 막지 못합니다.

[ 쇼핑몰 서버 ] 주문 ID + 1회용 확인값 ──▶ [ 내부 인증·복호화 기능 ] 열쇠 없음 · 권한 발급 불가 주문·결제·승인 조건 직접 조회 ◀── 조건 통과 시 번호 1건만 응답 KMS 열쇠 접근 · 전 건 기록

번호를 암호화해 저장합니다

관리자가 재고를 올리면 처리 메모리에서 즉시 암호화하고, DB·디스크·로그에는 평문을 보관하지 않습니다. 업로드 임시 파일도 처리 직후 삭제합니다. DB가 유출되더라도 상품권 번호는 암호화된 값으로만 확인됩니다.

푸는 일은 쇼핑몰 서버가 하지 않습니다

복호화는 관리자 UI와 프로세스·계정을 분리한 내부 인증·복호화 기능이 수행합니다. 쇼핑몰 서버는 주문 번호와 사용자가 입력한 1회용 확인값을 전달할 뿐이며, 열쇠와 열람 권한을 만들 수 없습니다. 두 서버 사이 통로는 ㉠ 주문 1건의 열람 요청만 처리하고, ㉡ 서로 인증서로 상대를 확인하며(상호 인증), ㉢ 관리자 UI와 다른 기능은 호출할 수 없습니다.

푸는 조건을 내부 기능이 직접 검사합니다

① 요청한 사람이 그 주문의 주인인가 ② 그 주문의 결제가 완료되었는가 ③ 그 회원이 번호 열람 승인을 받았는가 — 쇼핑몰 서버가 보내는 값을 그대로 믿지 않고 읽기 전용 DB 계정으로 주문 원장과 승인 상태를 직접 조회합니다. 셋 중 하나라도 아니면 복호화하지 않습니다. 번호 확인 시점에 등록된 전화번호로 1회용 코드를 보내 다시 확인하고, 주문 1건에 1장 · 유효 시간 3분 · 한 번 사용하면 폐기되는 단기 열람권을 발급합니다.

요청 총량을 제한하고 전부 기록합니다

복호화 요청 한도는 세 가지 축으로 적용합니다. 수치는 거래량을 알 수 없어 둔 초기값이며, G1에서 최근 3개월의 시간대별 정상 주문량을 확인해 확정합니다.

정당한 계정을 탈취당한 경우까지 가정합니다

아이디가 전화번호이면 계정 형식을 추측하기 쉽습니다. 그래서 ㉠ 로그인 시도 횟수를 제한하고 일정 횟수 실패 시 계정을 잠그며, ㉡ 번호를 열 때마다 알림톡으로 1회용 코드를 보내 재확인합니다. 비밀번호만으로는 번호까지 도달하지 못합니다.

축제한 (초기값)넘으면
계정당10분당 5건6번째 요청 차단 + 재인증 요구
쇼핑몰 서버 전체10분당 50건 또는 정상 최대치의 3배 중 큰 값다음 요청부터 복호화 통로 자동 차단 + 관리자 즉시 알림
패턴같은 접속원에서 10분 내 서로 다른 계정 5개 이상해당 접속원 차단 + 관리자 즉시 알림

「쇼핑몰 서버 전체」 축이 핵심입니다. 계정을 갈아 가며 한 건씩 요청해도 서버 전체 총량에서 차단합니다. 검수 때는 확정 임계값만큼 정상 요청을 보낸 뒤 임계값을 1건 넘긴 요청이 차단·기록·알림 처리되는지 확인합니다.

관리자 화면에서도 마음대로 볼 수 없습니다

이번 사고의 경로가 관리자 화면이었기 때문입니다. 관리자 화면의 번호는 기본적으로 가려져 있고(끝 4자리만 표시), 건별로 열 때 사유를 입력하고 2차 인증을 거치며, 하루 열람 건수 상한을 넘으면 자동 차단됩니다. 전체 내려받기 기능은 만들지 않습니다.

보호 범위 — 약속하지 않는 것

기본 2서버 구성은 DB 탈취와 쇼핑몰 서버 침해로 인한 평문 전량 유출을 막는 것이 목표입니다. 관리자 호스트의 시스템 관리자 권한, KMS 관리 계정, 정상 사용자의 브라우저까지 동시에 탈취된 상황을 무조건 차단한다고 약속하지 않습니다. 해당 범위까지 분리해야 하면 복호화 전용 제3 호스트 또는 HSM 구성을 별도 대안으로 제시하고 G1에서 선택받겠습니다.

회원 개인정보는 어떻게 다루는가

위 다섯 겹은 상품권 번호에 대한 것입니다. 회원 전화번호·주문 내역은 쇼핑몰 기능에서 사용해야 하므로 같은 복호화 서버 구조를 그대로 적용할 수 없습니다. 대신 ㉠ 전화번호는 조회용 해시값과 표시용 암호문을 분리하고, ㉡ 쇼핑몰 서버의 DB 계정에 필요한 표와 권한만 부여하며, ㉢ 수집 항목을 최소화하고(주민등록번호 미수집), ㉣ 관리자 조회 기록을 남깁니다. 「상품권 번호는 복호화 권한 분리, 회원 정보는 목적별 암호화·최소 권한·기록」으로 구분합니다. 보유·파기 기준은 회원·주문·결제·상품권·관리자 접속·번호 열람 기록별로 G1 요구사항 정의서에 표로 남깁니다. 법정 보존 대상은 필요한 기간만 보관하고, 기간이 지난 개인정보는 운영 DB와 백업의 보존 주기를 고려해 복구 불가능한 방식으로 순차 파기합니다.

검수 때 직접 확인하실 수 있습니다

발주사 입회하에 DB 전체를 덤프해 상품권 번호 칸을 열어 보는 것을 인수 기준 2번에 넣었습니다. 말로 하는 설명이 아니라 눈으로 보시는 것이 맞다고 생각합니다.

그래서 서버가 금액을 다시 계산합니다.

결제 금액 조작은 대부분 같은 방식으로 일어납니다. 브라우저가 서버로 보내는 값(상품 A, 금액 10,000원)을 중간에 금액 100원으로 바꿔 보내는 것입니다. 화면에서 금액 수정을 제한하더라도 브라우저 밖에서 요청값을 바꿔 보내면 차단할 수 없습니다.

브라우저가 보낸 값 : 상품 A, 수량 2, 금액 200원 ← 믿지 않습니다 서버가 다시 계산한 값 : 상품 A 단가 10,000 × 2 = 20,000원 PG사가 승인한 금액 : 20,000원 ────────────────────────────────────────── 세 값 중 뒤의 두 개가 같아야 주문이 확정됩니다
  • 주문 금액은 상품 마스터의 단가와 수량으로 서버가 계산하며, 브라우저가 보낸 금액은 쓰지 않습니다
  • 결제창에 띄우는 금액도 서버가 정합니다. 주문을 만들 때 서버가 금액이 담긴 주문 번호를 발급하고, 결제창은 그 번호로만 열립니다
  • PG 결제 승인 후 승인 금액과 서버 계산 금액을 대사합니다. 다르면 자동 취소하고 기록을 남깁니다
  • 결제 요청마다 한 번만 쓸 수 있는 주문 번호를 발급해 같은 결제가 두 번 처리되지 않게 합니다 (통합 빌링 시스템의 Transaction ID 중복 차단과 같은 구조)

사내 개발 인력이 없다고 적으셨으므로 단위부터 정의하고 시작합니다. 표준 산정과 공고 예산의 차이를 먼저 밝히고, 40 MD 안에서 수행할 범위와 조정 근거를 설명합니다. §4

1 MD (맨데이) = 참여 인력 1명이 1근무일에 수행하는 작업량 1 MM (맨먼스) = 30 MD (한 사람이 한 달 일하는 양으로 환산한 값) 10,000,000원 ÷ 250,000원/MD = 40 MD 40 MD ÷ 30 (1 MM = 30 MD) = 1.33 MM 40 MD ÷ 수행 기간 54달력일 = 달력 기간 환산 평균 0.74명

일정의 일수는 달력일이고, MD는 근무일 기준 작업량입니다. 참여율과 동시 투입 수치는 서로 다른 기간의 투입량을 비교하기 위해 54달력일에 나눈 기간 환산 평균입니다. 실제 작업은 영업일에 배치하며 주말 근무를 전제로 하지 않습니다. 0.74명은 상주 인원이 아니라 총 40 MD를 54달력일에 배분한 비교 지표이며, 실제 투입량과 비용은 역할별 MD를 기준으로 판단합니다.
